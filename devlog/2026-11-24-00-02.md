# 2026-11-24 00:02 — 开发环境搭建：Node + Electron + Wireclaw 联合开发

## 目标

让 `flowharness` 具备可运行、可验证的开发环境：

- pnpm workspace 管理 `apps/*` 与 `vendor/wireclaw`；
- wireclaw 作为 submodule 纳入，但**以普通库的方式被引用**（`import { Graph } from "wireclaw"`）；
- Electron 桌面壳可启动，main 与 renderer 都能加载 wireclaw；
- 留下可复现的验证命令与文档。

## 落地内容

### workspace 与依赖

- 根 `package.json`：`packageManager: pnpm@12.23.0`、聚合脚本（`dev` / `build` / `typecheck` / `smoke` / `watch:wireclaw` / `ensure:electron`）。
- `pnpm-workspace.yaml`：`apps/*`、`vendor/wireclaw`，以及 pnpm 12 的 `allowBuilds`（electron / esbuild）。
- `apps/desktop`：`flowharness-desktop`，依赖 `wireclaw: workspace:*`；工具链为 Electron 45.4.1 + electron-vite 6 + Vite 8 + TypeScript 7。

### wireclaw 联合开发

- 不改 submodule 内部结构，通过它既有的 `npm run build`（tsup + tsc 声明）产出 `dist/browser`、`dist/node`、`dist/types`。
- 根脚本 `build:wireclaw` / `watch:wireclaw` 负责构建；`watch:wireclaw` 用 concurrently 同时跑 tsup watch 与 tsc watch。
- 桌面端源码只写 `import { Graph } from "wireclaw"`；已用 Node 探针、tsc 类型检查、Vite 打包、Electron 运行四种方式验证解析正确。

### Electron 三端

- main：窗口生命周期、IPC、启动自检（构造一个 `Graph` 并打印）；
- preload：`contextBridge` 暴露 platform / versions / reportReady；
- renderer：原生 TS + CSS，展示运行时版本、wireclaw Graph 状态，并向主进程上报。

### 验证手段

- `pnpm typecheck`：node / web 两个 tsconfig project；
- `pnpm build`：wireclaw + desktop 全量构建；
- `pnpm smoke`：隐藏窗口启动已构建应用，校验 `[main] wireclaw ready` 与 `renderer-ready` 两个标记后退出。
- 另外单独跑过一次 `dev:no-sandbox`，确认 Vite 开发服务器（:5173）+ Electron 的 dev 路径可用。

## 踩坑与根因（重要）

### 1. 工作区 Windows 文件权限导致沙箱无法授权

DSH 会话在 `D:\Projects\Node\flowharness` 上授权失败（`SetNamedSecurityInfoW` 拒绝访问）。用诊断脚本补上当前用户对该目录的完全控制权限后恢复，未改动文件内容与所有者。

### 2. pnpm 12 的构建脚本配置变了

- `onlyBuiltDependencies` 不再适用，改为 `allowBuilds`，且是**映射**而非列表：

```yaml
allowBuilds:
  electron: true
  esbuild: true
```

### 3. Electron 二进制下载

- pnpm 不会把 `.npmrc` 里的 `electron_mirror` 透传给生命周期脚本（实测 `npm_config_electron_mirror` 为空），该写法无效，已删除 `.npmrc`。
- Electron 45 的 `index.js` 会在首次 `require("electron")` 时懒下载 `install.js`。
- 方案：`scripts/ensure-electron.mjs` 以 `ELECTRON_MIRROR`（默认 npmmirror）触发下载，命令 `pnpm ensure:electron`。

### 4. Electron 启动即崩溃（最关键）

现象：进程在打印第一条业务日志前后以 `0x80000003` / `0xC0000005` 退出，日志只有 allocator 信息。用最小探针逐步排除后得到三个独立原因：

1. **包名带作用域**：`"name": "@probe/name"` 的 app 必崩；改成无作用域名字即可。根因是 Electron 用 app name 拼 userData 路径，`/` 在 Windows 上非法。→ 桌面包改名 `flowharness-desktop`，显示名放 `productName`。
2. **userData 目录必须提前存在**：在本会话的受限环境下，Chromium 无法创建 `%APPDATA%\<AppName>`，目录不存在就崩在 `ready` 之前。→ `scripts/prepare-userdata.mjs` 在启动前用 Node 建好目录（`dev` / `smoke` 都会先跑它）。
3. **Chromium OS 沙箱无法初始化**：受限会话下直接启动就是 `STATUS_BREAKPOINT`，加 `--no-sandbox` 即正常。→ smoke 固定传 `--no-sandbox --disable-gpu`，并提供 `pnpm dev:no-sandbox`。

另外 `app.setName()` 在 `ready` 前调用会触发同一类崩溃（它会改变 userData 路径），因此不要提前 setName，改用 `productName`。

### 5. ESM 主进程的取舍

最初判断「Electron ESM main 崩溃」，改用 CJS。进一步定位后确认 ESM 崩溃其实是上面 userData 问题的表现，但**保留 CJS 仍是更稳的选择**：wireclaw 是 ESM-only，CJS 的 `require()` 无法直接加载，因此 main 构建时把 wireclaw 打包进 bundle（`externalizeDepsPlugin({ exclude: ["wireclaw"] })`），renderer 仍由 Vite 正常打包。源码层面始终只写包名。
